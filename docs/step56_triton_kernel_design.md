# step56 附篇：把验证搬进 kernel 的设计思路

这篇只讲**思路**：原来的做法差在哪、改成 GPU 批量之后内核该担什么责任、需要提前备好哪些输入、
以及哪些地方最容易做错。具体代码在 `step56/rejection_triton.py` 与 `step56/rejection.py`，
数据流与验证清单见 [step56_gpu_rejection.md](step56_gpu_rejection.md)。

开头先把两个反复出现的名词说清楚（counter RNG、指数竞赛）——后面 §一 第 3 条、§三 第 1 条都
以它们为前提，绕过去会很晕。

## 〇、先把两个名词说清楚

### 1. counter RNG：随机数 = F(密钥, 计数器)

**名字**：RNG 是 Random Number Generator（随机数生成器）的缩写；**counter 不是缩写**，
就是英文的「计数器」。合起来是「基于计数器的随机数生成器」。

它跟平常那种随机数生成器的差别，是**有状态**与**可查表**的差别：

| | 有状态（`torch.Generator`、C 的 `rand()`） | 基于计数器 |
|---|---|---|
| 怎么取数 | 调一次出一个，**内部状态往前走一格** | 直接给一个**编号**，问它「第 3 号是什么」 |
| 第 1000 个数 | 必须先抽掉前 999 个 | 直接算第 1000 个，前面一个都不用碰 |
| 中间少抽一次 | **后面全体错位** | 毫无影响 |
| 换顺序取 | 不行 | 随便取，同一个编号永远给同一个数 |

打个比方：有状态的像**抽牌**——抽一张少一张，顺序决定你拿到什么；基于计数器的像**一本印好的
电话簿**——「第 5 页第 3 行」永远是那个号码，你跳过几页直接翻过去，也不会影响别的行。

**实现上它就是一个纯函数**：`随机数 = F(密钥, 计数器)`。密钥决定「这是哪一条流」（一个请求
一辈子一条），计数器决定「这条流里的第几个」。这里的 `F` 用 **Philox-4x32-10**（Random123 那
套标准算法，10 轮「乘法 + 异或」混合），性质是**雪崩**：计数器差 1，输出看上去完全无关。
它一点也不神秘——`step56/rejection_rng.py` 里就是十几行纯 Python，与 GPU 内核**逐位一致**
（两万个事件的对照）。

**我们的「计数器」是四个整数拼起来的**：

```text
随机数 = F( 请求 seed， (事件编号, 事件类型, 词表 token 下标, 0) )
                            └─────────── 这就是"计数器" ───────────┘
```

实际取值举例：`F(seed=11, 事件编号=0, 类型=接受, token=0) = 0.8960479497909546`，问一万次都是
这个数。**把「词表 token 下标」放进计数器是刻意的**：这样「第 i 个候选 token 该用哪个随机数」
就成了一个**可以直接算出来**的问题，不必遍历、不必按顺序抽——这是「每个候选用自己的随机数」
这条语义能落到 GPU 上的唯一办法。

**为什么这一关非用它不可**：GPU 上要给整段 K **提前算好**候选随机数，而其中有些事件根本不会
发生（第一枚就被拒，后面的位置压根不判断）。有状态的流做不到「算过但没发生的事件不产生影响」；
基于计数器的天然做到——**没发生的事件，它的编号根本用不上，计数器自然不推进**。

### 2. 指数竞赛：给每个候选算一个「比赛值」，最小的赢

**先解释「词表规模」**：从一行权重里抽一个 token，最少也要把全部候选摸一遍（词表 15 万）。
而上面的随机数语义要求**每个候选 token 用自己的随机数**，于是一次抽样要算 15 万次 Philox——
这就是实测「一次抽样约 3ms」的来源。（对照：`torch.multinomial` 同样要摸一遍全部候选，但它
只需要**一个**随机数。）

**再说「竞赛」**。规则一句话：每个候选算一个比赛值，**取最小的那个**。

```text
e_i = -log(u_i) / w_i        u_i 是这个候选自己的随机数（落在 (0,1) 开区间）
赢家 = 使 e_i 最小的那个候选
```

**为什么这样就是对**（一句话版）：`-log(u)/w` 正好是「一个速率为 w 的闹钟响的时间」——
`u` 均匀分布时 `-log(u)` 服从速率为 1 的指数分布，除以 `w` 就是速率为 `w` 的闹钟。于是
「谁先响」的概率正好正比于 `w`，也就是**按权重抽样**。（数学上这就是 Gumbel-max 技巧的
另一种写法。）

手工能核对的一轮（权重 `[0.6, 0.3, 0.1]`，三个候选各抽到一个随机数 `u = [0.5, 0.2, 0.9]`）：

| 候选 | 权重 w | 随机数 u | 比赛值 `-ln(u)/w` |
|---|---|---|---|
| token 0 | 0.6 | 0.5 | 1.155 |
| token 1 | 0.3 | 0.2 | 5.365 |
| token 2 | 0.1 | 0.9 | **1.054** ← 最小 |

这一轮抽中 token 2。抽很多次，各自的频率会收敛到 `[0.6, 0.3, 0.1]`——实测六万次得到
`[0.6008, 0.2973, 0.1019]`。

**为什么不用「先建累计分布（CDF）再抽样」**：

1. **不需要归一化**：比赛值全体乘一个正常数，谁最小不变。所以纠正分布 `max(p−q, 0)` 那种
   和不为 1 的权重**不用**先归一化（归一化又要一遍全词表归约）。
2. **只要一个「取最小」**：可以一块一块（每块几千个候选）地流式比出最小值；CDF 要**前缀和**，
   那是跨候选的通信，更贵，也更难与 CPU 参考实现对到逐位一致。
3. **天然「每个候选用自己的随机数」**：正好满足第一节那条语义，现成的批量抽样算子给不了。
4. **边界好处理**：`w = 0` 的候选给正无穷 → 永远不赢（这就是「`max(p−q,0)` 的零质量不入选」
   的实现方式）；`u` 上加 0.5 保证它落在**开区间**，不会出现 `log(0)`。

代价就是「15 万次 Philox」。实测**大批才划算、小批反而亏**（1 条请求时比参考路径慢十倍，
16 条请求时才反超），取舍见 §五。

## 一、原来的代码哪里不好

### 1. 决策循环建在 CPU 上，所以每一步都要回读一个标量

原来的验证是「一条请求、一个 Python 循环」：逐位置判断这一枚草稿接不接受。判断要用到
`p[d]` 与 `q[d]`——它们算在 GPU 上，取回主机只能用 `.item()` / `float()`，而每次回读都是
一次**设备同步**加一次 4 字节拷贝。

实测（K=2、16 条请求，与验收方数出来的一致）：

| 请求数 | 触发设备同步的调用 | `aten::_local_scalar_dense` |
|---|---|---|
| 1 | 5 | 5 |
| 4 | 20 | 20 |
| 16 | **80** | **80** |

每一条请求 5 次：每枚草稿的 `p[d]`、`q[d]` 各一次，加一次纠正/bonus 抽样。每次回读的
**固定成本 25–40µs**（memcpy + 同步 + Python 调用开销），完全随请求数线性增长，而且全部
落在这一步的关键路径上。

### 2. 更麻烦的是：控制流依赖回读的值，所以既不能批量也不能预取

「这一枚接不接受」决定「还要不要验证下一枚」「要不要抽纠正」；抽出来的 token 又决定本轮
提交什么。这不是「写得笨」，而是**带数据依赖的决策链**：只能读一个、想一下、再读一个地乒乓。
想靠预取掩盖延迟也没用，因为下一个要读什么取决于上一个读回来的值。

### 3. 随机流是「顺序抽取」的，这跟「搬到 GPU」天生冲突

原来每条请求用一个 `torch.Generator` 顺序抽随机数。这个模型在 CPU 上没问题，可一旦决策要放到
GPU 上批量做，最自然的想法是「进验证时每条请求预抽 K 个随机数」——**这是错的**：第一枚就被拒、
或者第一枚就是终止 token 时，后面的位置根本没有发生判断，预抽却已经把随机数消耗掉了，下一轮
的事件位置就错位。真正的规则必须是「随机数只由**事件**决定，没发生的事件不占编号」，也就是
counter-based 随机数（随机数 = f(请求 seed, 事件编号, 事件类型, 词表 token 下标)；名词解释与
为什么非用它不可见 §〇 第 1 节）。

### 4. 结论逐请求返回，回传是分散的

每条请求构造一个对象、逐条回传。批一大，回传次数也跟着长。

### 5. 一个必须说清楚的边界（不然容易把需求的口号当实测结论）

在本引擎**当前**的工况下，CPU 侧 Python 才是大瓶颈：实测一次 target forward 的**入队**要
0.3–1 秒，而 GPU 真正跑完只要 1–7ms。所以在这个引擎里走到验证代码时，forward 早就跑完了，
回读并没有真的「等 GPU」（实测在验证前插一次 `torch.cuda.synchronize()` 只阻塞 0.06ms）。

那么这一关省下的是什么：**5N 次往返的固定成本与它们的串行化**（16 条请求 80 次 ≈ 2–3ms，
CPU 在这段时间里干不了别的），而不是「等待时间」。需求那句「反复让 CPU 等 GPU」描述的是
GPU 成为瓶颈的工况（批量大、CPU 侧已经被图模式和更少的 Python 削薄）——那时第一次回读确实
必须等 forward 跑完。两种情况都要认，不能只挑对自己有利的那一种说。

## 二、如果要改成 kernel，内核要负责什么

### 判据

**凡是控制流依赖 GPU 上算出来的值、并且决定接下来在设备上算什么的事情，就必须在设备上决定。**
按这条判据过一遍原来的验证流程，能清楚地分成两堆。

### 内核必须负责的四件事

1. **顺序决策本身**。沿 K 个位置推进「接受前缀」：必接受就前进、必拒绝/抽中拒绝就停下、
   接受的那一枚若是终止 token 也停下。这条链**串行**且依赖设备上的值，只能由内核做。
   并行度不在这条链上——它只在请求维度：请求之间互不相干，所以「一个 program 管一条请求」。
2. **随机数的产生与消费记账**。按事件编号算随机数，并且**由内核自己数**「这一轮真的消费了
   几个事件」。这一点没法外包：只有内核知道哪些分支真的发生了。记账错了，这条请求后续所有轮
   的随机流都会错位，而且错得很隐蔽（分布看着还是对的）。
3. **在未归一化的权重行上抽一个 token**。这一步能用 GPU 做，靠的是一个具体性质：把「按权重
   抽样」换成「对每个候选算一个指数分布的比赛值、取最小」，就只需要**归约**，不需要跨候选的
   通信，也不需要前缀和、不需要归一化。这恰好也满足了「每个候选用自己的随机数」这条语义
   要求——而现成的批量抽样算子（`torch.multinomial`）表达不了这种「按 token 下标取随机数」。
4. **把结论压成极少数几个标量**。每条请求只需要：接受了几枚、为什么停下（全接受/首拒绝/
   接受终止）、消费了几个事件、有没有错误，外加抽到的那一枚 token。内核不负责别的形态。

### 内核**不该**负责的（这条同样重要）

- **不算 p、q 本身，不做惩罚、不构造分布**。那些是批量的元素级运算，torch 一次算子就完成，
  放进内核只会更难写、更慢，也让「惩罚历史逐行不同」这类逻辑散到两个地方。
- **不碰请求状态**。不提交 token、不回滚 KV、不推进请求的计数器。内核只产出**结论**；
  状态变更留在采样层，按固定顺序做（先整批检查、再按顺序提交）。
- **不做词表级的归一化或排序**。归一化对结果没有影响（比赛值的 argmin 与整体定标无关），
  排序更是白花钱。
- **不做数据依赖的筛子集**。「只有需要抽样的那些行才进内核」听起来省，但筛子集会带来
  数据依赖的形状，那是一次隐式回传，等于把刚省掉的往返又加回来。

## 三、要准备哪些输入

总原则：内核只认**形状固定、能一次加载**的张量；所有 ragged 结构（每条请求的 K 可以不同）
必须在**主机侧**先摊平——主机侧算下标不花钱、也不产生同步，而设备侧一旦出现「按数据决定形状」
就会同步。

具体要备四类料。第 1 条最容易卡住，先展开讲。

### 1. 两套坐标系的下标

**先看「一行」是什么。** 一条投机请求本轮喂给目标模型的是「待定 token + K 枚草稿」
（K 枚草稿各占一个位置），模型因此算出 **K+1 行**分布：第 j 行是「第 j 个位置之后该出什么
token」的分布。于是：

- 第 0 行**正好用来判第 0 枚草稿**，第 1 行判第 1 枚……第 K−1 行判最后一枚草稿；
- 第 K 行没有人判——它是「全都接受之后再加一枚」用的，也就是 **bonus 行（收尾行）**。

**为什么会有两套编号**：因为要问的问题分两种，而且两种的「格子数」不一样。

| 要问的问题 | 谁问 | 怎么编号 |
|---|---|---|
| 「第 j 枚草稿的接受概率是多少」 | 接受决策，逐枚走 | **位置编号**：只数草稿，每项 K 个格子，总数 ΣK |
| 「拒绝之后 / 全接受之后，拿**哪一整行**当权重」 | 抽样，一次取一整行 | **行编号**：每项 K+1 个格子（多的那格就是 bonus 行），总数 Σ(K+1) |

两个总数的差正好是「每项多一行」——多出来的就是 bonus 行。**它只存在于行编号里**：bonus 行
不对应任何一枚草稿、不做接受判断，位置编号里没有它的位置，它唯一的用途是被抽一次。

**举个具体例子**：一批三项，K 分别是 2、0、1。

```text
项0  K=2   输入 [x0, d0, d1]      项1  K=0   输入 [x1]      项2  K=1   输入 [x2, e0]
 行 0  判 d0                        行 3  唯一一行          行 4  判 e0
 行 1  判 d1                        （没有草稿位置）        行 5  bonus（收尾行）
 行 2  bonus（收尾行）

行编号（每项 K+1 格）：  项0 = 行 0,1,2   项1 = 行 3   项2 = 行 4,5
                        行起点表 [0, 3, 4]        总数 Σ(K+1) = 6
位置编号（每项 K 格）：  项0 = 位置 0,1    项1 = （没有） 项2 = 位置 2
                        位置起点表 [0, 2, 2]，每项的 K 表 [2, 0, 1]   总数 ΣK = 3
                        位置上放的草稿 token = [d0, d1, e0]
「位置 → 行」映射 = [0, 1, 4]      ← 这张表把两套编号接起来
```

注意两处细节：`位置起点表[1] == 位置起点表[2] == 2`（K=0 的项不占位置，内核靠「K=0」
直接跳过它那一趟）；而它在**行编号里必须占一格**（行 3），因为 K=0 的回退项也要抽一枚 token。

**四种查询分别落在哪套编号上**（假设项 0 首枚被拒、`accepted = 1`）：

| 查询 | 编号 | 怎么算 | 本例 |
|---|---|---|---|
| 每个位置的接受概率 p[d]/q[d] | 位置 | 该位置的**行** = 映射表[位置]，token = 位置上那枚 | 位置 0 → 行 0（token d0） |
| 每个位置是不是终止 token / 非法输入 | 位置 | 同上 | — |
| 纠正权重取哪一行 | 行 | 行起点 + **运行期才知道的** accepted | 行 0 + 1 = 行 1 |
| bonus 权重取哪一行 | 行 | 行起点 + K（就是收尾行） | 行 0 + 2 = 行 2 |
| 被拒的那一枚 token 是谁 | 位置 | 位置起点 + accepted | 位置 0 + 1 = 位置 1 → d1 |

第二列为什么不能统一成一套：**「行起点 + accepted」里的 accepted 只有设备上才知道**（它是
上一枚接受与否的结果），这个加法必须在设备上做。所以行编号必须是一套**全局连续、设备自己能
算**的编号，而不是「每项各自一个小数组」那种结构——否则内核里每一步都要先定位「我在哪一项」，
就得按项分支。

**为什么两张表都必须在主机侧算好**：K 各不相同的 ragged 结构没法用规整张量表示，但摊平之后
每个位置、每一行都是一个整数编号；这些编号全部来自 Python 侧已知的元数据（每项提了几枚草稿），
在主机侧算不花钱、也不产生同步。

**最容易踩的坑**：图省事只用位置编号（或者行编号里不放收尾行）。那么「全接受时取第 K 行」
在位置编号里根本不存在——你会读到**下一项的第一行**；而设备上的高级索引**不查边界、不报错**，
读回来的是一个看着很正常、其实属于别人的分布。

### 2. 每个位置一个标量，提前在设备上算好

接受概率（有 q 时是 p[d]/q[d]，ngram 时退化成 p[d]）、这一枚是不是终止 token、以及它是不是
非法输入（q[d] 为零这种）。内核只负责读，不负责推导——推导是批量的元素级运算，属于 torch 那侧。

### 3. 每项的随机流参数

请求 seed、本请求已消费的事件数（计数器）、本项的 K 与本项在位置坐标系里的起点。另外每项还要
带「是不是贪心」——贪心不抽任何随机数，接受判断是纯比较。

### 4. 抽样要用的料

每项的权重行（纠正/bonus 各取哪一行由停止类型决定，行号在设备上算、一次高级索引取出来），
以及「被拒的那一枚 token」（ngram 用「挖掉它」的纠正分布，一般 q 用它去取 q）。还要备好输出侧
的容量约定：每项最多 K+1 枚 token、字段列宽按批内最大 K 定，连「整批 K 全为 0」这种退化形状
也要留出哨兵列。

**准备阶段自己也有纪律**：这一段的活必须保持**批量张量运算**。要是准备阶段又写成「一条请求
一段 Python 循环、再回读一个标量」，那只是把同步点从验证挪到了准备，白忙一场。

## 四、要注意什么

按「错了以后最难发现」的顺序排：

1. **随机数语义（最容易错、最难发现）**
   - 事件编号 = 本请求**已消费**的事件数 + 本轮第几次真的抽。必接受、必拒绝、贪心、
     终止 token 之后都不消费；报错的项只算它真的抽过的那些接受事件，不算没发生的抽样。
   - 32 位随机整数怎么变成能用的浮点，两种用途要分开：接受判断要 [0,1) 且 CPU/GPU **位同**
     （取高位定标）；抽样要**全部 32 位熵**。绝不能拿 [0,1) 的浮点再转回整数去用——那样只剩
     高几位，值恒等于 0，算出来的比赛值是垃圾：**接受判断全对、抽出来的 token 全错**。
   - 未播种的请求不能退化成同一个种子，否则所有这类请求的随机流完全相关，比「不可复现」更糟。
2. **形状纪律**：任何数据依赖的形状都是隐式同步；退化形状（批里混 K、整批 K=0）要提前定列宽
   与哨兵。默认「不筛子集、全都算、结论再丢」。
3. **越界与非法**：设备上的越界索引**不会报错**——高级索引会安静地读到别人的数据，而
   scatter 这类算子会直接让 CUDA 报设备断言。凡是「用运行期算出来的下标」都要过一遍：
   在每一种停止类型下它可能是什么范围？该夹住就夹住。
4. **循环携带变量的类型**：真循环里跨迭代必须保持类型一致；把循环按编译期上限展开可以绕开
   这条纪律，但展开也有代价（代码体积、编译时间），要看循环上限大不大。
5. **精度与边界**：概率、对数用双精度；随机数要落在 (0,1) **开区间**（避免 log(0)/log(1)）；
   零权重给正无穷而不是 0，否则要么除零要么误选。
6. **并列行为与 CPU 参考一致**（取最小下标）。「逐位对照」这类测试对并列极其敏感，
   参考实现与内核不一致时，通过率会低到让你怀疑随机数。
7. **职责边界**：内核不碰请求状态；结论要**整批算完再整批检查**、之后才按固定顺序提交，
   否则会出现「报错时已经提交了半批」。验证顺序与提交顺序必须解耦。
8. **可验证性**：内核里每一处「两种写法都说得通」的地方，都要配一个**能分辨**的对照用例。
   往 CPU 参考方向对齐、与参考实现逐位/逐事件比对，是唯一能在没出问题时也证明「它对」的办法。
   本关真实抓到的两个例子：布局里少一行收尾行（安静地读到别人的分布）、被拒位置没夹住
   （scatter 直接设备断言）。两个都是「不报错就发现不了」的类型。

## 五、这套设计的代价（要说在前面）

- **抽样内核是词表规模的**：每个候选都要算一次随机数，词表 15 万时一次抽样约 3ms 量级。
  实测同一张 16 条请求的批：参考路径 5.6ms、GPU 批量 3.8ms（**反超**）；但 1 条请求时
  参考路径 0.37ms、GPU 批量 3.7ms（**反而慢十倍**）。**大批才划算，小批反而亏。**
  这个代价是「随机数按 token 下标取」这条语义要求的（见 §〇 第 2 节），不是实现偷懒——
  现成的批量抽样算子表达不了这个语义。
- **没有消除全部同步**：每步仍有若干次固定的元数据上传（与请求数无关，是 O(1) 而不是 O(N)）。
  判据因此是「同步点数与批大小无关」，不是「同步次数为零」。
- **只覆盖「验证」这一环**：普通（非投机）采样仍用原来的生成器；提议阶段的 Python 开销与
  它自己的回读一点没动。**别把局部优化说成全引擎没有同步。**
