# step56 附篇：同一件事的两种取舍——我们与 vLLM 的拒绝采样对比

对照对象：本机 `vllm 0.28.0`，主要看 `vllm/v1/sample/rejection_sampler.py`（953 行）与
`vllm/v1/spec_decode/`、`vllm/v1/worker/gpu_model_runner.py`。

写这篇的原因：读自己这版代码时容易产生「怎么这么绕」的怀疑。对照之后结论是——**同一件事，
两边的密度差不多（我们三个文件 1011 行 vs 它 953 行），但复杂度的分布不同，而且它用几条
假设换掉了我们最费劲的那几块**。哪些是需求逼出来的、哪些是我们自己选的，这篇分清楚。

## 1. 逐项对照

| 维度 | vLLM 0.28 | 我们 | 备注 |
|---|---|---|---|
| **批内 K 不整齐** | padding 到 `max_spec_len`，哨兵 `-1`：「-1 is used for padded draft token ids that should be rejected」（`rejection_sampler.py:809`） | 扁平化 + 两套坐标系（行空间 Σ(K+1) / 位置空间 ΣK） | 他们**拿算力换简单**（每条请求都按最大 K 算），我们**拿下标算术换不浪费** |
| **随机数** | `generate_uniform_probs()`（`:608`）：每请求**预抽 K 个 uniform**，用该请求自己的 `torch.Generator`；K=0 的**跳过**（「Do not generate random numbers for requests with no draft tokens. This can be important for reproducibility.」，`:651`） | counter RNG：随机数 = f(seed, 事件编号, token 下标)，逐事件记账 | **我们复杂得多**（见 §3 第 1 条） |
| **贪心 / 随机** | **两个内核分开**：`rejection_greedy_sample_kernel`（`:714`）与 `rejection_random_sample_kernel`（`:773`） | 一个内核 + 每项一个 `is_greedy` 标志 | **他们更清爽**，我们更密 |
| **纠正分布** | 另起内核 `sample_recovered_tokens_kernel`（`:872`）预先抽好「恢复 token」，拒绝内核直接取用 | 同一个内核里按 `kind` 取权重行 + 指数竞赛 | 他们拆开、我们融合 |
| **`q[d] = 0`** | 「While the draft probability should never be 0, we check it to avoid NaNs. If it happens to be 0, we reject.」（`:828`） | 报**错误码 1**（契约：从 q 里抽不出一个 q 质量为零的 token） | 同一个防御点，**两种政策**：它悄悄拒绝，我们响亮报错 |
| **EOS** | 内核里**没有 EOS 概念**（`grep -c eos` = 0）：停不停由调度器的 stop 逻辑管 | `KIND_ACCEPTED_EOS` 是内核里的一个停止类型 | 需求要求「接受 EOS 就当场停、之后一个随机数都不许抽」，于是多出这个轴 |
| **编译特化** | `do_not_specialize=["max_spec_len"]`：一个内核服务所有 K，循环是运行时的 | `KMAX` 编译期展开（`tl.static_range`） | 他们省编译；我们省掉「循环携带变量必须同类型」那套纪律 |
| **测试手段** | `SYNTHETIC_MODE`：用合成的接受率跳过真实模型 | CPU oracle + 与内核逐位/逐事件对照 | 不同手段，同一目的 |
| **周边规模** | `spec_decode/` ≈ 17,000 行、`gpu_model_runner.py` 8,011 行；多种提议器、多硬件后端、分布式、LoRA、指标 | 一个包，单机单卡 | 它是大系统里的一层，我们是把它切一片放进一个包 |

## 2. 「它更好读」基本都来自**它敢假设**

把上面那几条假设单拎出来看，每一条都省掉我们一整块代码：

| 它的假设 | 省掉了什么 |
|---|---|
| 批内 K 用 padding 对齐 | 省掉两套坐标系、`row_offsets` / `pos_offsets` / `proposal_row_index` 这些下标表 |
| 随机数预抽、每轮按 K 推进生成器 | 省掉事件编号、消费记账、32 位边界、K=0 的路由问题（它用「跳过」解决） |
| `draft_prob` 理论上不会是 0 | 省掉一条错误通道与对应契约（它只防 NaN） |
| 内核不管 EOS | 少一个 `kind` 取值、少一片掩码、少一条「消费数为 0」的用例 |
| 贪心与随机分两个内核 | 每个内核只服务一种情形，不必在核心里按项掩码分流 |

反过来，**我们这版看起来更绕，是因为需求不允许这些假设**：

| 多出来的轴 | 谁要求的 |
|---|---|
| 事件编号 + 逐事件消费记账 | 需求 §4（随机数 = f(seed, 事件编号, 事件类型, token 下标)；没发生的事件不占编号） |
| 接受 EOS 当场停、之后不消费 | 需求（第五十四关起就定死的约定） |
| 非法输入报错（`q[d]=0`、无剩余质量、贪心落进随机分支、事件编号越界） | 需求：不能悄悄改用别的行为 |
| 与 CPU 参考逐位一致 | 本关的判据（不是「统计上像」） |
| ragged 而不浪费（K=2/0/1 混批，K=0 也要走同一套随机流） | 我们自己选的（第五十五关的 K=0 回退项 + 191/192 号验收） |

## 3. 三个值得记住的对照细节

**① 同一个问题，两种解法：K=0 的请求怎么保持可复现。**
它：预抽时**跳过** K=0 的请求（不推进生成器），所以「这一轮没有草稿」不影响后续随机流。
我们：K=0 的投机行**照样走** counter RNG（判据是 `speculative`，与草稿数无关），因为一条请求
一旦进了 decode，它的随机机制就不该再变。
两个解法都在防同一件事——**「有没有草稿」这种运行结果不该改变随机流**。差别是它靠「什么都不做」
防，我们靠「继续用同一套流」防。

**② 同一个防御点，两种政策。**
`q[d] = 0` 在它那里是「不可能发生，但为防 NaN 就当拒绝」；在我们这里是**错误码 1**。
原因不是我们更严格，而是**契约不同**：我们的 q 由调用方（提议层）提供，所以「草稿不是从这份 q
抽出来的」是可能的调用错误，必须报出来；它的 q 由内核自己算，天然不会为 0。

**③ 内核里「融合」是行业常态，不是我们的毛病。**
它的随机内核也是把「padding 哨兵 / 合成模式 / 没有 q / 正常路径」四种情况掩码在一个循环里
（`draft_token_id < 0`、`SYNTHETIC_MODE`、`NO_DRAFT_PROBS` 三个分支 + `tl.where`）。
**GPU 上按项分支要么做不到（设备值不能当条件）、要么会引入同步**，所以「少数函数 + 掩码」是
这个领域的写法。可读性的补偿手段两边也一样：命名、不变量、以及把「哪些组合被排除在外」写清楚
（见 [状态空间地图](step56_state_space.md)）。

## 4. 一条实用的读法

读 vLLM 这类代码时，**先找它用哪些假设换掉了什么**——找到假设，复杂度立刻塌下来一半；找不到，
再去看它的索引算术。同理，读我们自己这版时，先看它**不许**假设什么（那些就是需求逼出来的轴）。

## 5. 这篇的边界

- 只读了 `v1/sample/` 与 `v1/spec_decode/` 的一小部分，没有通读 `gpu_model_runner.py`；
- 对照的是功能与结构，**没有做性能对比**（本关不承诺加速）；
- 它有些东西我们没有、也不打算有（合成的接受率、多种提议器、多硬件后端、指标）；
- 我们有些东西它不需要（事件级随机流、与 CPU 参考逐位一致、接受 EOS 的当场停止语义）。
