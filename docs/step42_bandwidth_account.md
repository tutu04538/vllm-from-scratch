## 2. 单位与范围：先分清两个对象

原报告把「28 层的四种投影」与「一次 decode 的全部 Linear」混在一起，并且 MiB 与 MB 混用。
按验收意见改正：

**记法**：MiB = 2²⁰ 字节，MB = 10⁶ 字节。

| 类别 | 次数 | 权重形状 `[N,K]` | 权重 MiB | 权重 MB |
|---|---:|---|---:|---:|
| qkv | 28 | `[4096,1024]` | 224 | 234.88 |
| o | 28 | `[1024,2048]` | 112 | 117.44 |
| gate_up | 28 | `[6144,1024]` | 336 | 352.32 |
| down | 28 | `[1024,3072]` | 168 | 176.16 |
| **四种投影小计** | 112 | — | **840** | **880.80** |
| **lm_head** | 1 | `[151936,1024]` | **296.75** | **311.16** |
| **全部 Linear 合计** | 113 | — | **1136.75** | **1191.97** |

原报告的 `840 MB` 应为 **840 MiB ≈ 880.80 MB**；`qkv + gate_up` 是
**560 MiB ≈ 587.20 MB**。**`lm_head` 是原报告漏掉的一项**，它占了四种投影的 1/3。

**本文后面只分析四种投影（112 次），不含 `lm_head`。** 分析范围与时间分母必须一致——
验收 §3 指出：若比较引擎的「全部 GEMM」时间，分母里要计入 `lm_head`；
只分析四种投影时，时间分母也只能是这四种。

### 2.1 算法有效字节，不是流量计数

```python
M, N, K, layers = 8, 1024, 2048, 28          # 以 o_proj 为例
useful_bytes = layers * 2 * (N*K + M*K + M*N)
# 118,816,768 bytes；其中权重 117,440,512 bytes
```

这叫**算法有效字节估算**——按「权重与输入各读一次、输出写一次」算出来的。
**它不是硬件计数器读到的外部显存流量。** 激活项占比小（8×1024 对 1024×2048），
但**不能直接写成零**；上表与下文的带宽都按含激活的估算算。

## 3. 本机可达带宽：两种参考（实测）

| 参考 | 时间 | 有效 GB/s | 三进程范围 |
|---|---:|---:|---|
| `copy_` 256 MiB（读+写） | 1.025 ms | 523.9 | 523.4 ~ 524.1 |
| `copy_` 2048 MiB（读+写） | 5.799 ms | **740.7** | 736.5 ~ 748.6 |

数据来自验收方三个独立进程的补测（`验收记录/step42_review/bandwidth_summary.json`）。

**这是两种特定访问模式的参考值，不是所有 kernel 的统一上限。**
`copy_` 是连续的读+写；GEMM 是另一套访问模式，两者不能互相冒充。

## 4. 四种投影的有效带宽（实测）

同样引自验收方的三进程补测（每项 CUDA Graph + CUDA Event，取三进程中位数的中位数）：

| 形状 | N | K | 权重 MiB | 时间 ms | **有效 GB/s** | 三进程范围 |
|---|---:|---:|---:|---:|---:|---|
| qkv | 4096 | 1024 | 224 | 0.343 | 691.8 | 647.1 ~ 708.6 |
| gate_up | 6144 | 1024 | 336 | 0.485 | 732.7 | 495.3 ~ 733.4 |
| **o** | **1024** | 2048 | 112 | 0.372 | **319.8** | 292.9 ~ 336.6 |
| **down** | **1024** | 3072 | 168 | 0.585 | **304.1** | 302.6 ~ 364.9 |
| 四种连续 × 28 | — | — | 840 | 2.318 | **383.8** | 376.3 ~ 438.2 |

我自己用 `benchmarks/step42_bandwidth_account.py` 跑出的四种投影遍历中位是 **2.12 ms**
（权重口径约 415 GB/s），与上面 2.318 ms / 383.8 GB/s 同量级——**现象是可复现的**。

**注意这是合成投影微基准，不是完整模型 forward**；几行分别捕获计时，
不能把独立中位数相加当作整步时间。

## 5. 观测、假设、验证要分开

### 5.1 观测（已经测到）

- `o`/`down` 的有效带宽（约 300~320 GB/s）明显低于 `qkv`/`gate_up`（约 690~730 GB/s）。
- 用真实模型一步 eager decode 关联到的实际 grid（验收方实测，`real_decode_projection.json`）：

| 类别 | 实测 grid | CTA 总数 | block |
|---|---|---:|---|
| qkv | `(8,32,1)` | 256 | `(32,1,1)` |
| **o** | `(8,8,1)` | **64** | `(32,1,1)` |
| gate_up | `(8,48,1)` | 384 | `(32,1,1)` |
| **down** | `(8,8,1)` | **64** | `(32,1,1)` |
| lm_head | `(8,1187,1)` | 9496 | `(32,1,1)` |

- 设备属性返回 **82 个 SM**。

### 5.2 假设（还没有验证）

> `o`/`down` 每次发射 **64 个 CTA，少于本机 82 个 SM**；并行度受限可能是有效带宽偏低的
> 原因之一。

**到此为止。** 原报告写的「只有 8 个 CTA」是我按 128×128 分块**猜**的，实际 grid 是
`(8,8,1)`（cutlass 的 16×16 tile，所以第二维是 8 不是 8 个 CTA 的 8）——
**猜错了，且被当成了已验证的事实**。

同样不能写的是「低带宽唯一来自网格过小、只能靠 split-K 解决」。**观察 → 假设 → 验证
是三步，本关只走到第二步。** 本关不实现 split-K。

### 5.3 有效带宽 ≠ 实际显存带宽

`有效带宽 = 算法估算的有用字节 / 实测时间`。若部分读取命中了 L2，分子仍按完整权重计算，
结果**就可能超过 `copy_` 的测量值——这不是「物理上不可能」**。

原报告看到 `gate_up` 在某次测量中得到 1035 GB/s，就断言「超过上界、物理上不可能」，
并据此推翻整个逐形状微基准。**那个断言本身是错的**：它混淆了有效带宽与硬件流量。
改用 28 套互不相同的权重确实是有价值的改进（减少了 L2 命中），但**不等于证明每个字节
都来自外部显存**。

本次 Nsight Compute 返回 `ERR_NVGPUCTRPERM`，**没有拿到 DRAM 读写计数**。
所以本文所有数字严格称为**有效带宽**，不冒充真实外部显存流量。

另外：本机 RTX 5090 Laptop 用 **GDDR7**，本文统一写「外部显存」，不称 HBM
（原报告用了 HBM，已改）。

## 6. 时间账：原报告在这里错了

原报告写「账算出的 2.13 ms 落在引擎实测 2.2~2.5 ms 区间内，所以账是准的」。
**2.13 不在 2.2~2.5 区间内**（验收 §3 直接指出）。**这句话不能用，账没有因此闭合。**

可用的说法只有：合成微基准测得的四种投影遍历是 2.12~2.32 ms，与引擎里 GEMM 分类的
量级相当；但两者口径不同（一个只含四种投影，一个含 `lm_head` 与其它），
**不能直接说二者吻合**。

用权重字节算的估算：

```text
880.80 MB / 770 GB/s  ≈  1.144 ms
```

**这是一个建立在访问假设上的估算，不是已经证明的耗时下界。** 原报告把它叫作
「下界约 1.09 ms」（还用了错的 840 MB 与 770 的口径），两处都不对。

## 7. 未覆盖的范围

**attention / RMSNorm / RoPE / 其它 kernel 都没有建立带宽账。** 本关只做了
Linear 类的四种投影（外加 `lm_head` 的字节数，未做时间归因）。

**不要把这份局部诊断写成完整归因。** decode 一步里 attention 占约 13%、其它约 10%、
RMSNorm 约 4%、RoPE 约 1%（需求 §1 的表），这些都没有账。

## 8. 探索性观察（保留，但不作为已验证结论）

下面两条**没有保留对应的可复现脚本与原始结果**，按验收 §7 第 3 条标为探索性观察：

1. 比较 `x @ w.T` / `F.linear(x, w)` / `x @ w.t()` 三种写法，在同一口径下结果接近
   （约 320 GB/s）。**一次进程内的少量样本，不等于三个独立进程的结论，也不足以断言
   「瓶颈不在调用方式」。**
2. 把 `down_proj` 权重存成 `[K,N]` 连续时观察到更快（约 370 → 537 GB/s）。
   即便成立，**需求 §3 明确要求「权重布局不变」，这条不能走**，所以也没有继续验证。

## 9. 当前基线与 vLLM（验收方同会话重测）

单位是**整组请求完成的墙钟毫秒**，不是单步 GPU 时间：

| 负载 | 当前基线 | vLLM | 我们 / vLLM |
|---|---:|---:|---:|
| short_c1 | 91.97 | 96.92 | 0.949× |
| short_c8 | 130.33 | 124.65 | 1.046× |
| prefill_c1 | 12.89 | 12.83 | 1.005× |
| prefill_c8 | 82.99 | 83.31 | 0.996× |
| decode_c1 | 391.79 | 377.67 | 1.037× |
| **decode_c8** | **542.00** | **448.16** | **1.209×** |

**`decode_c8` 约慢 21%，不能继续把「只差 5%~16%」当作固定事实。**
不过源码没变，不能据此说第四十二关引入了回退；也不能仅凭六个离线负载宣称
「运行时优化已经走完」。

## 10. 接口变化与遗留

**接口变化：无。** 没有新建实现版本，`step41/` 未改。

**遗留**：

1. `o`/`down` 的有效带宽偏低**只有观测与一个假设**，没有因果验证；本文已按此收窄措辞。
2. **没有拿到 DRAM 计数器**（`ERR_NVGPUCTRPERM`），所有带宽都是有效带宽口径。
3. **attention / norm / RoPE 没有带宽账**，本关的归因范围就是 Linear 的一部分。
4. §8 的两条是探索性观察，缺可复现证据。
5. `decode_c8` 当前 1.209×，方向可以转到里程碑④（持续到达负载：长跑稳定性、尾延迟、
   抢占恢复），但那需要先解释 c8 这 21% 从哪来——它比本关分析的投影差距更大。
