# step49：增量维护空闲 KV 块

从 `step48/` 复制。`step48/` 原样保留，未改。**改动只有 `cache.py` 一个文件。**

## 结论

剖析测到：32 请求 / 8192 块的调度负载里 `schedule()` 累计 45 ms，其中 43 ms 花在补块——
因为「真正空闲」是每次**临时扫全池**算出来的，而多数时候只想拿 1 块。池子越大这份无用功越大。

改成在 `KVCachePool` 里**增量维护一个空闲队列**：

```python
self.free_queue = deque(range(num_kv_blocks))
```

- 计划阶段**只读**：`_peek_free_blocks(k)` 用 `islice` 看队首前 k 个，**不取走**
  （计划失败不得有副作用）。
- 提交阶段才 `_pop_free_blocks(k)`，从队首取走。
- 释放时**只有引用数 1→0 且该块不带 prefix hash**才 `append` 到队尾。
  prefix 缓存块是「闲置缓存」，**不是**「真正空闲」，不入队。
- 初始按编号升序、释放的块排到队尾——与本机 vLLM `FreeKVCacheBlockQueue` 的顺序语义一致。

> 初版用的是**最小堆**（每次挑编号最小的空闲块，好与 `step48` 逐步对照）。
> 明确「空闲块顺序不必与前面 step 一致」之后换成 `deque`：更简单，性能也测不出差别。

闲置缓存的 LRU 扫描**原样保留**——那是下一种瓶颈，不在这一关混着改。

## 效果（3 次独立运行，原始数据在 `benchmarks/results/`）

`_plan_block_growth(seq, 1)` 中位耗时（μs）：

| 池子块数 | 占用形态 | step48 | step49 |
|---|---:|---:|---:|
| 256 | 真正空闲 | 5.16–5.36 | **0.29** |
| 4096 | 真正空闲 | 102.24–106.93 | **0.28–0.29** |
| 16384 | 真正空闲 | 420.69–433.81 | **0.42–0.44** |
| 16384 | 闲置 prefix 缓存 | 1419.59–1457.40 | 982.63–1013.51 |

**真正空闲路径从「随池子线性增长」变成常数**。`idle_cached` 仍线性（走的是下一关的 LRU 扫描）。

32 请求 / 8192 块 / prefix 关：`schedule()` 累计从 **40.9–42.1 ms** 降到 **1.8–3.2 ms**；
池子 1024 → 8192 的劣化从 **6.6 倍**降到 **1.0–1.9 倍**。`_reserve_blocks()` 从 40 ms 降到 0.5–0.8 ms。

**这不是端到端吞吐结论**——剖析已说明调度 CPU 开销在当前小模型里还不是端到端主瓶颈。
