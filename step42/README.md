# step42：decode 一步的 GPU 带宽账 —— 归因关，无实现改动

**这个目录不是代码包。** 第四十二关是**归因关**：需求 §7 明确说「先把账建起来，
**一行代码都不用改**」。本关没有新建实现版本，`step41/` 一个字节没改。

> 与 [`step36/`](../step36/README.md) 同类：诊断关，产物是结论与数据，不是代码。

## 1. 结论

> 已观察到 `o`/`down` 的**有效带宽偏低**，但**尚未证明唯一瓶颈**。在当前证据下，
> 不继续投入 GEMM 专项，先保留实现；这是一项工程取舍，**不是证明不存在其它优化空间**。

**这个措辞是验收方给的、也是本关唯一站得住的力度。** 更早的版本写过「原因已确定、
只有 split-K 一条路、收益天花板 0.44 ms」，那几处都被收窄成了假设或条件估算。

## 2. 字节账（修正过单位与范围）

MiB = 2²⁰ 字节，MB = 10⁶ 字节。

| 类别 | 次数 | 权重形状 `[N,K]` | 权重 MiB | 权重 MB |
|---|---:|---|---:|---:|
| qkv | 28 | `[4096,1024]` | 224 | 234.88 |
| o | 28 | `[1024,2048]` | 112 | 117.44 |
| gate_up | 28 | `[6144,1024]` | 336 | 352.32 |
| down | 28 | `[1024,3072]` | 168 | 176.16 |
| **四种投影小计** | 112 | — | **840** | **880.80** |
| **lm_head** | 1 | `[151936,1024]` | **296.75** | **311.16** |
| 全部 Linear 合计 | 113 | — | 1136.75 | 1191.97 |

两个容易搞混的对象：**「28 层的四种投影」不等于「一次 decode 的全部 Linear」**——
后者还要加一次 `lm_head`。**本关只分析四种投影（112 次），不含 `lm_head`。**
分析范围和时间分母必须一致。

这些是**算法有效字节估算**（权重与输入各读一次、输出写一次），不是硬件计数器读到的
外部显存流量。激活项占比小但不能记作零。

## 3. 有效带宽（实测）

参考值：`copy_` 256 MiB → 523.9 GB/s；`copy_` 2048 MiB → **740.7 GB/s**
（验收方三进程补测）。这是**一种访问模式的参考，不是所有 kernel 的统一上限**。

| 形状 | 权重 MiB | 时间 ms | **有效 GB/s** | 三进程范围 |
|---|---:|---:|---:|---|
| qkv | 224 | 0.343 | 691.8 | 647.1 ~ 708.6 |
| gate_up | 336 | 0.485 | 732.7 | 495.3 ~ 733.4 |
| **o** | 112 | 0.372 | **319.8** | 292.9 ~ 336.6 |
| **down** | 168 | 0.585 | **304.1** | 302.6 ~ 364.9 |
| 四种连续 ×28 | 840 | 2.318 | 383.8 | 376.3 ~ 438.2 |

我自己跑 `benchmarks/step42_bandwidth_account.py` 得到四种投影遍历中位 **2.14 ms**
（约 412 GB/s），与上表同量级 —— **现象可复现**。

**一律叫「有效带宽」，不叫显存带宽。** 本次 Nsight Compute 返回 `ERR_NVGPUCTRPERM`，
**没有拿到 DRAM 读写计数**。有效带宽可以因为 L2 命中而高于外部显存带宽，
这是口径差异，**不是「物理上不可能」**（早前的版本在这里下过错断言）。

另外：本机是 **GDDR7**，统一写「外部显存」，不称 HBM。

## 4. 观测与假设要分开

### 观测（测到了）

- `o`/`down` 有效带宽约 300~320 GB/s，明显低于 `qkv`/`gate_up` 的约 690~730 GB/s。
- 真实模型一步 eager decode 关联到的**实测 grid**（验收方）：

| 类别 | grid | CTA 数 | block |
|---|---|---:|---|
| qkv | `(8,32,1)` | 256 | `(32,1,1)` |
| **o** | `(8,8,1)` | **64** | `(32,1,1)` |
| gate_up | `(8,48,1)` | 384 | `(32,1,1)` |
| **down** | `(8,8,1)` | **64** | `(32,1,1)` |
| lm_head | `(8,1187,1)` | 9496 | `(32,1,1)` |

- 设备属性：**82 个 SM**。

### 假设（未验证）

> `o`/`down` 每次发射 **64 个 CTA，少于本机 82 个 SM**；并行度受限可能是有效带宽
> 偏低的原因之一。

**只能写到这里。** 早前版本写的「只有 8 个 CTA」是按 128×128 分块**猜**的，
实际是 `(8,8,1)`（cutlass 的 16×16 tile）——**猜错了，还被当成了实测**。
同样不能写「唯一原因是网格过小、只能靠 split-K」。

**观察 → 假设 → 验证是三步，本关只走到第二步。**

## 5. 时间账：早前在这里算错过

早前写过「账算出的 2.13 ms 落在引擎实测 2.2~2.5 ms 区间内，所以账是准的」。
**2.13 不在 2.2~2.5 区间内**（验收直接指出），这句话不能用，**账没有因此闭合**。

能说的只是：合成微基准测得四种投影遍历 2.12~2.32 ms，与引擎里 GEMM 分类的量级相当；
但两者口径不同（一个只含四种投影，一个含 `lm_head` 与其它 kernel），**不能说二者吻合**。

用权重字节估：`880.80 MB / 740.7 GB/s ≈ 1.19 ms`。
**这是建立在访问假设上的估算，不是已证明的耗时下界。**

## 6. 未覆盖的范围

**attention / RMSNorm / RoPE / 其它 kernel 都没有带宽账。** decode 一步里
attention 约占 13%、其它约 10%、RMSNorm 约 4%、RoPE 约 1%。

**不要把这份局部诊断写成完整归因。**

## 7. 探索性观察（不作为已验证结论）

下面两条**没有保留可复现脚本与原始结果**：

1. 三种调用写法（`x @ w.T` / `F.linear(x, w)` / `x @ w.t()`）结果接近（约 320 GB/s）。
   一次进程内的少量样本，**不等于三个独立进程的结论**，不足以断言「瓶颈不在调用方式」。
2. `down_proj` 权重存成 `[K,N]` 连续时观察到更快。即便成立，**需求 §3 要求
   「权重布局不变」**，这条不能走，也没有继续验证。

## 8. 当前基线 vs vLLM（验收方同会话重测）

单位是**整组请求完成的墙钟毫秒**：

|---|---:|---:|---:|
| short_c1 | 91.97 | 96.92 | 0.949× |
| short_c8 | 130.33 | 124.65 | 1.046× |
| prefill_c1 | 12.89 | 12.83 | 1.005× |
| prefill_c8 | 82.99 | 83.31 | 0.996× |
| decode_c1 | 391.79 | 377.67 | 1.037× |

**`decode_c8` 约慢 21%**，不能再说「只差 5%~16%」。源码没变，不能据此说本关引入了回退；
也不能仅凭六个离线负载宣称运行时优化已经走完。

## 9. 复现

## 11. 遗留

1. `o`/`down` 偏低**只有观测与一个假设**，没有因果验证。
2. **没有 DRAM 计数器**，所有带宽都是有效带宽口径。
3. attention / norm / RoPE **没有带宽账**。
4. §7 两条缺可复现证据。
5. `decode_c8` 当前 1.209×——**这 21% 比本关分析的投影差距更大**，
   解释它之前谈"转向其它方向"没有意义。

**本关最该记住的一条**（验收 §7 原话）：把「测到了什么」和「所以我猜什么」分开写。
早前版本把三件事混在一起了——猜的分块尺寸当成实测 grid、有效带宽当成物理上界、
局部诊断当成完整归因。修正的不是数字，是**证据等级**。
